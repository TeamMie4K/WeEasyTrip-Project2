ABSTRACT

This project presents a system that creates and optimizes budget-constrained tourist routes using artificial intelligence. It solves the Budget-Constrained Team Orienteering Problem with Time Windows (B-TOPTW) with a Greedy Algorithm, a Genetic Algorithm (GA) and a proposed Hybrid Algorithm. After a Phuket prototype (Special Project 1), this report extends the system to all 77 provinces (four main provinces with 720 points of interest, the rest generated from OpenStreetMap), and adds re-optimization after user edits, user preferences, and calendar/PDF export.
Under realistic-schedule rules, experiments over four provinces and three scenarios (15 trials each) show that the Hybrid Algorithm scores significantly higher than GA in 12 of 12 settings (2.4-5.5%) while satisfying all constraints in every run. Re-optimization raises the number of feasible plans after user edits from 137 to 180 of 180 cases. Scores and prices of the new provinces are estimates.

Keywords: Thailand Tourism, Artificial Intelligence, Genetic Algorithm, Hybrid Algorithm, Travel Route Optimization, Team Orienteering Problem, OpenStreetMap

## ความเป็นมาและความสำคัญของโครงงาน
การวางแผนท่องเที่ยวมีความซับซ้อนและใช้เวลามาก นักท่องเที่ยวต้องค้นข้อมูลสถานที่จากเว็บไซต์รีวิว แอปพลิเคชันแผนที่ แพลตฟอร์มจองที่พัก และโซเชียลมีเดียพร้อมกัน แล้วรวบรวมและเปรียบเทียบข้อมูลเหล่านั้นด้วยตนเอง
ระบบแนะนำการท่องเที่ยวที่มีอยู่ส่วนใหญ่แสดงเป็นรายการสถานที่แยกจากกัน หรือจัดเส้นทางจากระยะทางเพียงอย่างเดียว โดยไม่คำนึงถึงงบประมาณรวม เวลาเปิด-ปิด ระยะเวลาในแต่ละจุด การจัดมื้ออาหาร และการเริ่มต้น-สิ้นสุดที่โรงแรมพร้อมกัน ผู้ใช้จึงต้องวางแผนต่อเอง
ในเชิงทฤษฎี ปัญหาดังกล่าวจัดอยู่ในกลุ่ม Team Orienteering Problem with Time Windows (TOPTW) ภายใต้ข้อจำกัดด้านงบประมาณ ซึ่งเป็นปัญหา NP-hard ไม่สามารถแก้ด้วย exact algorithm ได้ในเวลาที่ยอมรับได้เมื่อจำนวนสถานที่เพิ่มขึ้น จึงต้องอาศัย metaheuristic เช่น Genetic Algorithm (GA), Simulated Annealing (SA), หรือ Ant Colony Optimization (ACO) เพื่อให้ได้คำตอบที่มีคุณภาพดีในเวลาที่เหมาะสม
โครงงานนี้นำเสนอระบบสร้างและเพิ่มประสิทธิภาพเส้นทางท่องเที่ยวภายใต้งบประมาณด้วยปัญญาประดิษฐ์ ในโครงงานพิเศษ 1 ผู้จัดทำสร้างต้นแบบที่ใช้จังหวัดภูเก็ตจังหวัดเดียวเพื่อพิสูจน์ความเป็นไปได้ รายงานฉบับนี้ (โครงงานพิเศษ 2) ต่อยอดต้นแบบดังกล่าวใน 3 ด้าน คือ
- (1) ขยายให้ใช้ได้ทั้ง 77 จังหวัด โดยใช้ข้อมูลที่คัดและตรวจแล้วของ 4 จังหวัดหลัก (ภูเก็ต เชียงใหม่ กระบี่ เกาะสมุย) เป็นชุดทดลองหลัก และสร้างข้อมูลจังหวัดที่เหลือจาก OpenStreetMap อัตโนมัติ
- (2) ปรับแผนใหม่ด้วย Hybrid หลังผู้ใช้แก้ไข และรองรับความชอบของผู้ใช้
- (3) ส่งออกแผนเป็นไฟล์ปฏิทินและ PDF
โดยเปรียบเทียบ Greedy Algorithm (baseline), Genetic Algorithm และ Hybrid Algorithm เพื่อยืนยันว่า Hybrid ให้ผลดีกว่าทั้งด้านคุณภาพคำตอบและการรองรับข้อจำกัดหลายข้อพร้อมกัน
## วัตถุประสงค์
โครงงานนี้มีเป้าหมายเพื่อพัฒนาระบบต้นแบบที่สร้างและเพิ่มประสิทธิภาพเส้นทางท่องเที่ยวภายใต้งบประมาณที่ผู้ใช้กำหนด ด้วย Greedy Algorithm, Genetic Algorithm และ Hybrid Algorithm และขยายจากต้นแบบบนจังหวัดภูเก็ตเป็นระบบที่ใช้ได้ทั้ง 77 จังหวัด จึงกำหนดวัตถุประสงค์ดังนี้
- 1. นิยามปัญหา Budget-Constrained Team Orienteering Problem with Time Windows (B-TOPTW) ในเชิงคณิตศาสตร์ ที่ครอบคลุมข้อจำกัดด้านงบประมาณ เวลาเปิด-ปิดของสถานที่ ระยะเวลาในแต่ละจุด และการเริ่มต้น-สิ้นสุดที่โรงแรม
- 2. พัฒนาระบบต้นแบบที่ใช้ Genetic Algorithm ในการแก้ปัญหา B-TOPTW โดยรองรับการสร้าง 3 packages อัตโนมัติ (Budget / Standard / Premium) ตามระดับงบประมาณ
- 3. พัฒนาฟังก์ชัน custom package ที่ให้ผู้ใช้สามารถเปลี่ยนสถานที่ในแต่ละวันได้ และระบบทำการ re-optimize เส้นทางและคำนวณค่าใช้จ่ายใหม่แบบอัตโนมัติ
- 4. ทดสอบและเปรียบเทียบประสิทธิภาพของ 3 อัลกอริทึม คือ Greedy Algorithm (baseline), Genetic Algorithm, และ Hybrid Algorithm (ที่นำเสนอใหม่ในโครงงาน) บนชุดข้อมูลสถานที่ท่องเที่ยวในจังหวัดภูเก็ต (โครงงานพิเศษ 1) และ 4 จังหวัด (โครงงานพิเศษ 2) โดยวัดทั้งคุณภาพคำตอบ (total score), เวลาที่ใช้ (runtime), และความสมจริงของ schedule (days with POIs)
- 5. พัฒนาเว็บไซต์ที่นำเสนอระบบในรูปแบบที่ใช้งานได้จริง โดยแสดงเส้นทางบนแผนที่และตารางค่าใช้จ่ายอย่างชัดเจน
- 6. ขยายระบบให้ใช้ได้ทั้ง 77 จังหวัด โดยสร้างกระบวนการสร้างข้อมูลสถานที่และโรงแรมของจังหวัดใหม่จาก OpenStreetMap และปรับเทียบเวลาเดินทางรายจังหวัดด้วย OSRM
- 7. ปรับปรุง Hybrid Algorithm ให้ปรับแผนใหม่หลังผู้ใช้แก้ไข (re-optimization) คำนึงถึงความหลากหลายของหมวดสถานที่ และรองรับความชอบของผู้ใช้ (หมวดที่ชอบหรือไม่เอา อาหารมังสวิรัติหรือฮาลาล)
- 8. ให้ผู้ใช้ส่งออกแผนเป็นไฟล์ปฏิทิน (.ics) และ PDF
- 9. วิเคราะห์ความไวของพารามิเตอร์ที่เลือกเอง วินิจฉัยผลที่ผิดคาด และทดสอบซอฟต์แวร์ เพื่อประเมินความน่าเชื่อถือของผลการทดลอง
## ขอบเขตของโครงงาน
โครงงานนี้กำหนดขอบเขตการพัฒนาและการทดสอบไว้ดังนี้
- 1. ขอบเขตครอบคลุมการท่องเที่ยวในประเทศไทยทั้ง 77 จังหวัด โดยชุดข้อมูลหลักที่ใช้ทดลองมี 4 จังหวัด ได้แก่ ภูเก็ต (181 สถานที่ 20 โรงแรม) เชียงใหม่ (224 สถานที่ 26 โรงแรม) กระบี่ (145 สถานที่ 25 โรงแรม) และเกาะสมุย (170 สถานที่ 28 โรงแรม) รวม 720 สถานที่และ 99 โรงแรม (ข้อมูลภูเก็ตเป็นชุด 164 สถานที่ที่คัดเองในโครงงานพิเศษ 1 เสริมร้านมังสวิรัติและฮาลาลจาก OSM อีก 17 ร้าน) และมีข้อมูลที่สร้างอัตโนมัติจาก OpenStreetMap อีก 74 จังหวัด รวมเป็น 77 จังหวัด
- 2. ระยะเวลาทริปที่ระบบรองรับอยู่ที่ 1-7 วัน โดยทุกวันเริ่มและสิ้นสุดที่โรงแรมเดียวกัน และยังรวมถึงการท่องเที่ยวแบบ One-day trip
- 3. งบประมาณที่ระบบรองรับอยู่ในช่วง 1000 - 100,000 บาทต่อทริป (ครอบคลุม day-trip ราคาถูกถึงทริปหรู)
- 4. อัลกอริทึมที่เปรียบเทียบมี 3 ตัว ได้แก่ Greedy Algorithm (baseline), Genetic Algorithm และ Hybrid Algorithm (Greedy seed + GA refinement + local search ที่นำเสนอใหม่) ผู้ใช้สลับอัลกอริทึมได้จาก UI
- 5. ระบบเป็นแบบ web-based ที่ใช้งานบน browser ทั่วไป โดยใช้ Python (FastAPI) เป็น backend และ HTML/JavaScript กับ Leaflet.js เป็น frontend
- 6. โครงงานนี้ไม่ครอบคลุมการดึงข้อมูลแบบ real-time จาก Google Maps หรือ TripAdvisor การจองโรงแรม-ตั๋วทัวร์ การคิดค่าเดินทางตามสภาพการจราจรจริง การ login ของผู้ใช้ และการแจ้งเตือนสภาพอากาศแบบอัตโนมัติ (ระบบแสดงเฉพาะพยากรณ์ฝนรายวันจาก Open-Meteo ในหน้าแผน)

ในด้านวิชาการ โครงงานนำเสนอกรณีศึกษาเชิงประยุกต์ของ Genetic Algorithm กับปัญหา TOPTW ที่มี budget constraint เพิ่มเติม รวมถึง realistic schedule constraints (มื้ออาหารตามช่วงเวลาจริง, ความหลากหลายของหมวดสถานที่) ซึ่งสามารถใช้เป็นพื้นฐานในการต่อยอดงานวิจัยด้าน Tourist Trip Design Problem (TTDP) ในบริบทของประเทศไทยได้
ในด้านการประยุกต์ใช้งาน นักท่องเที่ยวที่วางแผนทริปในประเทศไทยสามารถใช้ระบบเพื่อรับคำแนะนำเส้นทางและค่าใช้จ่ายโดยประมาณภายในเวลาไม่กี่วินาที ลดเวลาในการค้นข้อมูลและจัดตารางทริปด้วยตนเอง โดยปัจจุบันครอบคลุม 4 จังหวัด ผู้ใช้ปรับแผนและระบุความชอบได้ และส่งออกแผนเป็นไฟล์ปฏิทินหรือ PDF
ในด้านการต่อยอดเทคโนโลยี กระบวนการสร้างข้อมูลจังหวัดจาก OpenStreetMap ทำให้ขยายไปจังหวัดอื่นได้ และสามารถต่อยอดด้วยข้อมูลจริงจากบริการภายนอก (ราคาโรงแรม รีวิว เวลาเปิด-ปิด) รวมถึงการประยุกต์ใช้ Generative AI ในอนาคต
ในด้านการเรียนการสอน source code และ dataset ของโครงงานสามารถใช้เป็นตัวอย่างประกอบการเรียนวิชาที่เกี่ยวข้องกับ Optimization, Metaheuristics, และ Algorithm Analysis ในระดับปริญญาตรี


## ข้อจำกัดของโครงงาน
โครงงานนี้มีข้อจำกัดที่ผู้ใช้และผู้พัฒนาต่อยอดควรทราบดังนี้
- 1. ฐานข้อมูลสถานที่ท่องเที่ยวเป็น static dataset ที่จัดเตรียมไว้ล่วงหน้า ไม่ได้อัปเดตตามข้อมูลจริงแบบเรียลไทม์ ค่าใช้จ่ายและช่วงเวลาเปิด-ปิดอาจเปลี่ยนแปลงตามฤดูกาล
- 2. ข้อมูลของจังหวัดเชียงใหม่ กระบี่ เกาะสมุย และจังหวัดอื่นอีก 74 จังหวัด สร้างอัตโนมัติจาก OpenStreetMap คะแนนสถานที่เป็นค่าประเมินจากความสมบูรณ์ของข้อมูล ไม่ใช่คะแนนรีวิวจริง ราคาโรงแรมประมาณจากจำนวนดาว ราคาร้านอาหารประมาณจากประเภทอาหาร และเวลาเปิด-ปิดใช้ค่าเริ่มต้นตามหมวดเมื่อไม่มีข้อมูล
- 3. เวลาเดินทางคำนวณจากระยะทางถนนและความเร็วเฉลี่ยของถนนว่างที่ปรับเทียบด้วย OSRM รายจังหวัด ไม่รวมสภาพการจราจรจริง เช่น ช่วงเร่งด่วนในเมืองใหญ่ ซึ่งอาจทำให้ใช้เวลาจริงนานกว่าแผน (ระบบชดเชยด้วยตัวคูณการจราจร 1.25 และเวลาเผื่อ 10 นาทีต่อการย้ายจุด ซึ่งเป็นสมมติฐานที่ไม่ได้วัดจริง)
# วรรณกรรมและงานวิจัยที่เกี่ยวข้อง

## แนวคิดทฤษฎีที่เกี่ยวข้อง
ส่วนนี้นำเสนอแนวคิดทฤษฎีพื้นฐานที่เกี่ยวข้องกับโครงงาน ครอบคลุมปัญหาการจัดเส้นทาง อัลกอริทึมเชิงพันธุกรรม และการประเมินคุณภาพของคำตอบในปัญหา NP-hard
### Orienteering Problem (OP)
ปัญหา OP คือปัญหาการเลือก subset ของจุดบนกราฟ พร้อมจัดลำดับการเดินทาง โดยที่ผลรวมของ score (รางวัล) ของจุดที่เลือกสูงสุด ภายใต้ข้อจำกัดด้านระยะเวลา OP เป็นการ generalize ปัญหา Traveling Salesman Problem (TSP) ที่อนุญาตให้ไม่ต้องเดินทางผ่านทุกจุด ปัญหานี้ถูกพิสูจน์ว่าเป็น NP-hard ทำให้การแก้ด้วย exact algorithm ใช้เวลามากเมื่อจำนวนจุดเพิ่มขึ้น
### Team Orienteering Problem with Time Windows (TOPTW)
TOPTW เป็นการขยายปัญหา OP ใน 2 ทิศทาง คือ
- (1) มีหลายเส้นทาง (team) ทำให้สามารถใช้แทนทริปหลายวันได้
- (2) แต่ละจุดมีช่วงเวลาที่อนุญาตให้เข้าถึง (time window) เพิ่ม constraint ทำให้ปัญหาซับซ้อนขึ้น เหมาะสำหรับโจทย์การท่องเที่ยวที่สถานที่แต่ละแห่งมีเวลาเปิด-ปิดต่างกัน
### Genetic Algorithm (GA)
GA เป็น metaheuristic แบบ population-based ที่จำลองกระบวนการคัดเลือกตามธรรมชาติ ทำงานโดยรักษากลุ่มของคำตอบ (population) แล้วปรับปรุงคำตอบในแต่ละ generation ผ่าน 3 operator หลัก ได้แก่ Selection (คัดเลือก parent ที่ fitness ดี), Crossover (รวมยีนของ parent สองตัว), และ Mutation (สุ่มเปลี่ยนแปลงยีนเล็กน้อย) GA เหมาะกับปัญหา NP-hard ที่ search space ใหญ่ เพราะสามารถสำรวจ space ได้แบบขนานและไม่ติดกับ local optima ได้ง่ายเหมือน gradient-based methods
### Greedy Algorithm
Greedy Algorithm คือวิธีการแก้ปัญหาที่เลือกตัวเลือกที่ดีที่สุดในแต่ละขั้นตอน (locally optimal) โดยหวังว่าจะได้คำตอบที่ดีในภาพรวม ในโครงงานนี้ใช้ Greedy เป็น baseline สำหรับเปรียบเทียบกับ GA โดยเลือกจุดที่มี ratio ของ score ต่อ cost สูงสุดเสมอ Greedy มีข้อดีที่เร็วและ implement ง่าย แต่มักให้คำตอบที่ไม่ optimal เมื่อปัญหามี constraint หลายข้อ
### Iterated Local Search (ILS)
Local search คือการปรับปรุงคำตอบเดิมทีละน้อยด้วยการเปลี่ยนแปลงเฉพาะที่ (neighbourhood move) เช่น การแทนที่ การแทรก หรือการสลับตำแหน่ง แล้วรับคำตอบใหม่เมื่อดีขึ้น วิธีนี้เร็วแต่มักติดอยู่ที่ local optimum Iterated Local Search (ILS) [9] แก้ปัญหานี้โดยวนซ้ำระหว่างการค้นหาเฉพาะที่กับการสั่นคำตอบ (perturbation หรือ shake) แล้วเก็บคำตอบที่ดีที่สุดที่พบ Vansteenwegen et al. (2009) [7] ใช้แนวคิดนี้กับ TOPTW โดยอาศัยการแทรกสถานที่เข้าเส้นทางและการสั่นคำตอบ ในโครงงานนี้ ILS ทำหน้าที่ปรับปรุงแผนรายวันที่ Hybrid สร้างแล้ว ด้วยการแทนที่สถานที่ เติมช่องที่ว่าง และสั่นคำตอบโดยแทนที่ 2 จุดแบบสุ่ม (รายละเอียดในหัวข้อ 3.3.12)
### Multi-objective Optimization และ NSGA-II
ปัญหาหลายวัตถุประสงค์ไม่มีคำตอบเดียวที่ดีที่สุดสำหรับทุกวัตถุประสงค์พร้อมกัน แต่มีเซตของคำตอบที่ไม่ถูกครอบงำ (non-dominated) เรียกว่า Pareto front โดยคำตอบ A ครอบงำคำตอบ B เมื่อ A ไม่แย่กว่า B ในทุกวัตถุประสงค์และดีกว่าอย่างน้อยหนึ่งข้อ NSGA-II [10] เป็น GA หลายวัตถุประสงค์ที่จัดประชากรเป็นชั้น (front) ด้วย non-dominated sorting ใช้ crowding distance เลือกตัวที่กระจายอยู่บน front และคัดเลือกรุ่นถัดไปแบบ elitist สำหรับข้อจำกัดใช้ constraint-domination ที่ให้คำตอบที่ผ่านข้อจำกัดชนะคำตอบที่ไม่ผ่านเสมอ การวัดคุณภาพของ front ใช้ hypervolume [11] คือปริมาตรของพื้นที่ในปริภูมิวัตถุประสงค์ที่ถูก front ครอบงำเมื่อเทียบกับจุดอ้างอิง ยิ่งมากยิ่งดี (ในโครงงานประมาณค่าด้วยการสุ่ม) โครงงานนี้ใช้ NSGA-II เป็นทางเลือกเปรียบเทียบกับ Hybrid แบบถ่วงน้ำหนัก (หัวข้อ 3.3.14)
### Reinforcement Learning และ REINFORCE
Reinforcement Learning (RL) คือการเรียนรู้ของ agent ที่ตัดสินใจเป็นลำดับในสภาพแวดล้อมและได้รับรางวัล (reward) เพื่อเรียนรู้นโยบาย (policy) ที่ให้รางวัลสะสมสูงสุด REINFORCE [12] เป็นอัลกอริทึมแบบ policy gradient ที่ปรับพารามิเตอร์ของนโยบายไปในทิศที่เพิ่มรางวัลที่คาดหวัง โดยใช้รางวัลของแต่ละตอน (episode) ที่สุ่มได้ และมักลบ baseline เช่น ค่าเฉลี่ยของรางวัลเพื่อลดความแปรปรวนของการประมาณ ในโครงงานนี้นโยบายเป็น softmax เชิงเส้นที่เลือกสถานที่ทีละช่องของวัน และนำแผนที่ได้ไปเป็น seed ของ Hybrid (หัวข้อ 3.3.14)
## งานวิจัยที่เกี่ยวข้อง
### งานวิจัยของ Vansteenwegen และคณะ (2011)
Vansteenwegen et al. (2011) [1] ทำ survey อย่างครอบคลุมเกี่ยวกับ Orienteering Problem และนำเสนอกรอบการจำแนกประเภทของปัญหาตาม constraint ที่เพิ่มเข้ามา รวมถึงอัลกอริทึมหลักที่ใช้ในการแก้ ตั้งแต่ exact algorithm จนถึง metaheuristic งานชิ้นนี้เป็นจุดอ้างอิงสำคัญในการนิยามปัญหาของโครงงาน
### งานวิจัยของ Gavalas และคณะ (2014)
Gavalas et al. (2014) นำเสนอ survey ที่มุ่งเน้นเฉพาะ algorithmic approach สำหรับ Tourist Trip Design Problem (TTDP) ซึ่งเป็นการประยุกต์ OP ในบริบทการท่องเที่ยว งานวิจัยชี้ว่า GA และ Tabu Search เป็น metaheuristic ที่ได้รับความนิยมมากที่สุดสำหรับ TTDP เนื่องจากความยืดหยุ่นในการรองรับ constraint หลายชนิด
### งานวิจัยของ Souffriau และคณะ (2008)
Souffriau et al. (2008) นำเสนอ Greedy Randomised Adaptive Search Procedure (GRASP) สำหรับ Team Orienteering Problem ผลการทดลองบน benchmark dataset ชี้ว่า GRASP สามารถให้คำตอบที่ใกล้เคียง optimal ในเวลาที่สั้นกว่า exact algorithm มาก งานนี้เป็นแรงบันดาลใจให้โครงงานเลือกใช้ metaheuristic
### ความแตกต่างของโครงงานนี้กับงานวิจัยข้างต้น
แม้งานวิจัยข้างต้นจะครอบคลุมการแก้ปัญหา OP/TOPTW อย่างกว้างขวาง แต่ส่วนใหญ่ใช้ benchmark dataset สังเคราะห์และไม่ได้นำเสนอในรูปแบบของระบบที่ใช้งานได้จริง โครงงานนี้แตกต่างใน 2 จุด คือ
- (1) ใช้ข้อมูลสถานที่ท่องเที่ยวจริงใน 4 จังหวัด (ภูเก็ต เชียงใหม่ กระบี่ เกาะสมุย)
- (2) เพิ่ม budget constraint ที่ครอบคลุมค่าเข้าชมและค่าอาหาร ซึ่งใกล้เคียงกับการใช้งานจริงของนักท่องเที่ยว (ค่าเดินทางไม่นับในงบ ดูหัวข้อ 3.3.6)

### นิยามปัญหา B-TOPTW เชิงคณิตศาสตร์
ปัญหาที่โครงงานแก้คือ Budget-Constrained Team Orienteering Problem with Time Windows (B-TOPTW) ซึ่งเป็นรูปแบบหนึ่งของ TOPTW ที่เพิ่มข้อจำกัดด้านงบประมาณและรูปแบบมื้ออาหาร นิยามดังนี้
- (1) ให้ V = A ∪ R เป็นเซตสถานที่ของจังหวัด โดย A คือสถานที่ท่องเที่ยว R คือร้านอาหาร และ h คือโรงแรมที่เป็นจุดเริ่มต้นและสิ้นสุดของทุกวัน ทริปมี D วัน (1 ≤ D ≤ 7)
- (2) สถานที่ i ∈ V มีคะแนน si ค่าใช้จ่าย ci (บาท) เวลาที่ใช้ δi (นาที) และช่วงเวลาเปิด-ปิด [oi, ei] (นาทีนับจากเที่ยงคืน) ส่วน B คืองบกิจกรรมของทริป (งบรวมหักค่าโรงแรมตามจำนวนคืน)
- (3) ให้ rij = ρ · dij เป็นระยะทางถนนโดยประมาณ เมื่อ dij คือระยะทางเส้นตรง (Haversine) ระหว่าง i และ j และ ρ คือ road factor ของจังหวัด เวลาเดินทางคือ
tij = 75 · rij / u + 10 · 1[rij ≥ 0.3]
เมื่อ u คือความเร็วเฉลี่ยของจังหวัด (กม./ชม.) ค่า 75 มาจาก 60 นาที × ตัวคูณการจราจร 1.25 และ 10 นาทีคือเวลาเผื่อจอดและเดินเข้าจุดเมื่อย้ายไกลตั้งแต่ 0.3 กม. (สองค่านี้เป็นสมมติฐานที่เลือกเอง)
- (4) เส้นทางวันที่ k คือลำดับ πk = (h, vk,1, …, vk,n_k, h) โดยทุกวันออกจากโรงแรมเวลา 08:00 ให้ ai คือเวลาที่เริ่มใช้บริการที่ i หลังรอเปิดร้าน (หรือรอถึงช่วงมื้อ)
วัตถุประสงค์คือเลือกสถานที่และจัดลำดับเพื่อให้คะแนนรวมสูงสุด
maximize  Σk=1^{D} Σi ∈ π_{k} si
ภายใต้ข้อจำกัดต่อไปนี้
- (C1) สถานที่แต่ละแห่งถูกเลือกได้ไม่เกิน 1 ครั้งตลอดทริป
- (C2) งบประมาณ: Σk Σi ∈ π_{k} ci ≤ B (ค่าเดินทางไม่นับในงบ)
- (C3) เวลาปิด: ai ≤ ei ทุกสถานที่
- (C4) รูปแบบวัน: แต่ละวันมีสถานที่ท่องเที่ยวไม่เกิน 4 แห่ง และร้านอาหาร 2 ร้าน (มื้อกลางวันเริ่ม 11:00-14:30 มื้อเย็นเริ่ม 17:00-20:00 ร้านแรกที่ถึงก่อน 15:30 นับเป็นมื้อกลางวัน)
- (C5) เวลาท่องเที่ยวต่อวัน Σi ∈ π_{k ∩ A} δi ≤ 480 นาที (ไม่รวมมื้อและการเดินทาง)
- (C6) เวลาทั้งวัน (ออก 08:00 จนกลับถึงโรงแรม) ไม่เกิน 840 นาที (กลับก่อน 22:00)
นอกจากนี้ มีเพดานงบรายวันที่ 1.1 เท่าของงบเฉลี่ยต่อวัน (1.1 · B / D) เพื่อกระจายงบข้ามวัน ซึ่งเป็นข้อจำกัดแบบแข็งใน Greedy และแบบอ่อนใน GA (ผ่านค่าปรับ)
อัลกอริทึม Hybrid ค้นหาโดยใช้ค่าเป้าหมายต่อวัน Fk ที่หักตัวลงโทษออกจากคะแนน เพื่อให้แผนไม่ขับไกลและไม่ยาวเกินไป ส่วนผลการทดลองรายงานคะแนนดิบ Σ si ไม่รวมตัวลงโทษ
Fk = Σi ∈ π_{k} si + w · Divk − 0.3 · Lk − 0.02 · Wk − 0.01 · Tk
เมื่อ Lk คือระยะขับรวมของวัน (กม.) Wk คือเวลารอก่อนมื้อ (นาที) Tk คือเวลาทั้งวัน (นาที) และ Divk = (จำนวนหมวดสถานที่ท่องเที่ยวที่ต่างกัน − 1) − Σc max(0, nc − 2) โดย nc คือจำนวนสถานที่ในหมวด c ของวันนั้น w = 1.5 ใน Hybrid+Div และ w = 0 ใน Hybrid ปกติ ปัญหา B-TOPTW เป็นปัญหา NP-hard เพราะเป็นกรณีทั่วไปของ Orienteering Problem (หัวข้อ 2.1.1)

### การจัดสรรงบประมาณตาม Tier
ระบบใช้กลยุทธ์ tier-based budget allocation เพื่อกระจายงบประมาณระหว่างค่าโรงแรมและค่ากิจกรรมอย่างสมเหตุสมผล โดยกำหนดเพดานสัดส่วนของงบรวมที่จะใช้กับค่าโรงแรมในแต่ละ tier ดังนี้ Budget tier (โรงแรม ≤ 20% + ใช้รวม ≤ 40% ของงบ), Standard tier (โรงแรม ≤ 45% + ใช้รวม ≤ 75%), Premium tier (โรงแรม ≤ 55% + ใช้รวม ≤ 100% ของงบ ใช้เต็มงบ) นอกจากนั้น Budget tier ใช้ scoring mode แบบ ratio (score/cost) และจำกัดราคาร้านอาหารไม่เกิน 150 บาท ขณะที่ Standard และ Premium ใช้ scoring mode แบบ quality (พิจารณา score เป็นหลัก) โดย Standard จำกัดราคาร้านอาหารไม่เกิน 400 บาท วิธีนี้ทำให้ Budget tier เลือกที่เที่ยวคุ้มราคา ขณะที่ Premium เลือกที่ดีที่สุดโดยไม่กังวลราคา
## การวิเคราะห์ขอบเขตและความต้องการของระบบ
จากการวิเคราะห์ความต้องการของผู้ใช้และข้อจำกัดของโครงงาน สามารถสรุปความต้องการของระบบได้ดังนี้
ความต้องการเชิงฟังก์ชัน (Functional Requirements) ประกอบด้วย
- (1) ระบบต้องสามารถรับ input จากผู้ใช้ ได้แก่ งบประมาณรวม จำนวนวัน จำนวนคน และการรวมงบโรงแรมไว้ในงบประมาณ
- (2) ระบบต้องสร้าง 3 packages ที่แตกต่างกันตามระดับงบประมาณ
- (3) แต่ละ package ต้องแสดงเส้นทางบนแผนที่ พร้อมตารางค่าใช้จ่ายและ score รวม
- (4) ระบบต้องอนุญาตให้ผู้ใช้เปลี่ยนสถานที่ในแต่ละวัน และคำนวณ route + cost ใหม่อัตโนมัติ
- (5) ระบบต้องรองรับการเลือกจังหวัด (ภูเก็ต เชียงใหม่ กระบี่ เกาะสมุย) โดยใช้ข้อมูลสถานที่และโรงแรมของจังหวัดที่เลือก
- (6) ระบบต้องปรับแผนใหม่ด้วย Hybrid เมื่อผู้ใช้สลับ เพิ่ม หรือลบสถานที่ โดยคงจุดที่ผู้ใช้เลือกและไม่นำจุดที่ลบกลับมา
- (7) ระบบต้องรองรับความชอบของผู้ใช้ ได้แก่ หมวดที่ชอบ หมวดที่ไม่ต้องการ และอาหารมังสวิรัติหรือฮาลาล
- (8) ระบบต้องส่งออกแผนเป็นไฟล์ปฏิทิน (.ics) และ PDF
ความต้องการที่ไม่ใช่เชิงฟังก์ชัน (Non-Functional Requirements) ได้แก่
- (1) เวลาตอบสนองในการสร้าง package ต้องไม่เกิน 10 วินาที สำหรับ N=40 จุด
- (2) เวลา re-optimize เมื่อ swap จุดต้องไม่เกิน 1 วินาที
- (3) UI ต้องใช้งานง่าย รองรับการดูบน desktop browser อย่างน้อย ผู้ใช้และฟังก์ชันที่ระบบรองรับแสดงในภาพที่ 3.3

### ท่อประมวลผลข้อมูล 77 จังหวัด
เพื่อขยายไปทั่วประเทศ โครงงานสร้างท่อประมวลผลข้อมูลอัตโนมัติ (data/build_all_provinces.py) ต่อจังหวัด ได้แก่ หาจุดศูนย์กลางตัวเมืองด้วย Nominatim กำหนดขอบเขตรอบจุด ±0.2 องศา ดึงสถานที่และโรงแรมจาก OpenStreetMap ผ่าน Overpass รวมร้านมังสวิรัติและฮาลาล เติมชื่ออังกฤษ ปรับเทียบเวลาเดินทางด้วย OSRM แล้วลงทะเบียนใน provinces.json เกณฑ์ขั้นต่ำต่อจังหวัดคือสถานที่ไม่น้อยกว่า 60 จุดและโรงแรมไม่น้อยกว่า 10 แห่ง ส่วนจังหวัดเล็กหรือชนบทที่ไม่ใช่ศูนย์กลางท่องเที่ยว (นอกเหนือจาก 15 จังหวัดศูนย์กลางท่องเที่ยว) ใช้เกณฑ์ผ่อนปรน คือสถานที่ไม่น้อยกว่า 20 จุดและโรงแรมไม่น้อยกว่า 2 แห่ง และทำเครื่องหมายเป็นข้อมูลแบบเบาบาง (sparse) จังหวัดที่ต่ำกว่าเกณฑ์จะไม่ลงทะเบียน คำค้น Overpass ที่ล้มเหลวลองใหม่สูงสุด 4 รอบ และจำกัดการค้นในเขตแดนจังหวัดจริงเพื่อไม่ให้ข้อมูลซ้อนกัน การดึงข้อมูลใช้เวลาจังหวัดละราว 1-1.7 ชั่วโมงเพราะ Overpass ฟรีมีคิวยาว และท่อทำงานต่อจากจุดที่ค้างได้ ปัจจุบันมีข้อมูลพร้อมใช้ครบ 77 จังหวัด ได้แก่ ภูเก็ต เชียงใหม่ กระบี่ (พร้อมเกาะสมุยในจังหวัดสุราษฎร์ธานี) และจังหวัดที่สร้างอัตโนมัติอีก 74 จังหวัด โดย 35 จังหวัดผ่านเกณฑ์ปกติและ 39 จังหวัดผ่านเกณฑ์ผ่อนปรน
### เวลาเดินทางรายจังหวัด
ต้นแบบแรกประมาณเวลาเดินทางจากระยะเส้นตรง (Haversine) และความเร็ว 40 กม./ชม. เท่ากันทุกจุด ระบบปัจจุบันปรับเทียบรายจังหวัดด้วย OSRM [14] (เครือข่ายถนนจริง) โดยสุ่มคู่สถานที่ 40 คู่ต่อจังหวัด คำนวณ road factor (ระยะถนนรวมต่อระยะเส้นตรงรวม) และความเร็วเฉลี่ย ได้ภูเก็ต 1.38 และ 45.8 กม./ชม. เชียงใหม่ 1.41 และ 47.6 กระบี่ 1.63 และ 42.2 เกาะสมุย 1.50 และ 51.6 ระบบนำค่านี้ไปใช้คำนวณเวลาเดินทางของทุกอัลกอริทึม โดยเก็บใน provinces.json เนื่องจากความเร็วที่ได้เป็นแบบรถไม่ติด จึงคูณเวลาเดินทางด้วยตัวคูณการจราจร 1.25 และบวกเวลาเผื่อหาที่จอดและเดินเข้าจุด 10 นาทีต่อการย้ายจุดที่ไกลกว่า 0.3 กิโลเมตร (ภูเก็ตระยะ 9 กิโลเมตร จากราว 12 เป็นราว 25 นาที) สองค่านี้เป็นสมมติฐานที่เลือกเอง ไม่ได้วัดจากการจราจรจริง และผลทดลองบทที่ 4 ทั้งหมดรันด้วยค่านี้
### กติกาความสมจริงของแผนรายวันและตัวตรวจแผนกลาง
ตัวตรวจแผนกลาง (evaluate_route) เป็นตัวเดียวที่ทุกอัลกอริทึมใช้ตัดสินว่าแผนผ่านข้อจำกัดหรือไม่ เพื่อให้เปรียบเทียบอัลกอริทึมได้เท่าเทียมและให้ทุกแผนปฏิบัติตามได้จริงในเชิงเวลา (หากควบคุมช่วงเวลามื้อเฉพาะในขั้น Greedy แผนจาก GA และ Hybrid อาจมีมื้อเย็นช่วงบ่ายหรือวันที่แน่นเกินไป) กติกาที่ใช้มีดังนี้
- (1) จำนวนจุดต่อวันคงที่ 6 จุด ตามรูปแบบ attr-attr-lunch-attr-attr-dinner ของโครงงานพิเศษ 1 คือสถานที่ท่องเที่ยวไม่เกิน 4 และร้านอาหาร 2 (วันที่เวลา งบ หรือจำนวนร้านอาหารไม่พอมีสถานที่ท่องเที่ยวน้อยกว่า 4 จุดได้) และห้ามเลือกร้านอาหารสองร้านติดกันเพื่อให้มีกิจกรรมคั่นระหว่างมื้อ
- (2) ช่วงเวลามื้อ: ร้านแรกของวันเป็นมื้อกลางวันต้องเริ่มภายใน 11:00-14:30 ร้านที่สองเป็นมื้อเย็นต้องเริ่มภายใน 17:00-20:00 ถ้าไปถึงก่อนเวลาต้องรอ (เวลารอนับรวมในเวลาต่อวันและถูกหักคะแนนเล็กน้อยใน fitness) ถ้าสายกว่านั้นถือว่าผิดข้อจำกัดและไม่ขยายช่วงเวลา เพื่อไม่ให้มีมื้อเย็นช่วงบ่าย และตรวจเวลาปิดร้านหลังรอแล้ว เพื่อไม่ให้ร้านที่ปิดก่อนเย็น (เช่น ปิด 15:30) ถูกนับว่าไปมื้อเย็นได้ ใน Greedy ระบบบังคับเลือกร้านเมื่อถึง lunch trigger (11:30) และ dinner trigger (17:00) โดยข้ามเวลาไปที่เวลามื้อเพื่อให้ทุกวันมีทั้งสองมื้อ
- (3) เพดานเวลาท่องเที่ยว 480 นาที (8 ชั่วโมง) ต่อวัน ไม่รวมมื้ออาหารและการเดินทาง และวันต้องจบก่อน 22:00 พร้อมกลับโรงแรม
- (4) กิจกรรมที่เปิดเฉพาะช่วงค่ำ (เปิดหลัง 17:00 เช่น โชว์ ตลาดกลางคืน) จัดไว้หลังมื้อเย็น
- (5) งบรายวันไม่เกิน 1.1 เท่าของค่าเฉลี่ย เพื่อกระจายงบข้ามวันและป้องกันวันแรกใช้งบหมด (เป็น hard constraint ใน Greedy และ soft constraint ผ่าน penalty function ใน GA)
- (6) โบนัสความหลากหลายสำหรับ POI ในหมวดที่ยังไม่มีในวันนั้น เพื่อกระจายชนิดสถานที่
เหตุผลที่ใช้ 6 จุดต่อวัน: ทางเลือกที่ผ่อนเพดานเป็นสถานที่ท่องเที่ยวไม่เกิน 5 จุดบวกอาหาร 2 และให้ ILS เติมจุดที่ 6 (รวม 8 จุด) ทำให้คะแนนรวมสูงขึ้น แต่การทดสอบบนหน้าเว็บพบว่าบางวันมี 7-8 จุดซึ่งผู้ใช้ไปไม่ครบหรือไม่มีเวลาเที่ยวพอ และต่างจากรูปแบบ 6 จุดของโครงงานพิเศษ 1 โดยไม่มีเหตุผลรองรับ จึงเลือก 6 จุดคงที่ และเพิ่มประสิทธิภาพของ 6 จุดนั้นด้วยการหักคะแนนระยะขับ เวลารอ และเวลาทั้งวัน (หัวข้อ 3.3.6 และ 3.3.12) แล้วให้ ILS แทนที่จุดแทนการเพิ่มจุด คะแนนรวมจึงต่ำกว่าแบบ 7-8 จุดโดยตั้งใจ เพราะแผนมีสถานที่น้อยลงแต่ไปได้จริงมากขึ้น
### ระยะขับ ต้นทุนเดินทาง และการเลือกโรงแรม
ระบบไม่นับค่าเดินทางเป็นเงินในงบ (COST_PER_KM = 0 งบ = ค่าเข้าชม + ค่าอาหาร) เพราะเมื่อนับ 10 บาทต่อกิโลเมตร ในกรณีทดสอบนครนายก (งบ 2,000 บาท ไม่รวมโรงแรม) ค่าเดินทางกินงบจนอัลกอริทึมตัดสถานที่ท่องเที่ยวฟรีทิ้งหมด (วันที่ 1 ขับ 155 กิโลเมตร ไปเพียง 3 จุด) แต่เมื่อไม่มีค่าเดินทาง แผนวิ่งวันละ 150-260 กิโลเมตร จึงควบคุมระยะขับด้วยการหักคะแนนระยะทางแทน (DIST_WEIGHT = 0.3 ต่อกิโลเมตร ใน hybrid.py และ ils.py) ค่านี้เลือกจากการทดลองเบื้องต้นกับนครนายกและภูเก็ต (ที่น้ำหนัก 0.03, 0.1, 0.2 และ 0.4 ระยะขับเท่ากับ 127, 93, 81, 72 กม./วันในนครนายก และ 43, 33, 29, 27 ในภูเก็ต โดยคะแนนรวมลดลงไม่ถึงร้อยละ 3) แล้วเลือกค่ากลาง 0.3 ผลของค่านี้ต่อข้อสรุปตรวจในหัวข้อความไวต่อพารามิเตอร์ (ตารางที่ 4.11) เพื่อให้เปรียบเทียบเท่าเทียม GA หักระยะทาง 0.3 ต่อกิโลเมตรใน fitness เท่ากับ Hybrid และ Greedy บวกค่าปรับ 10 บาทต่อกิโลเมตรของระยะจากจุดก่อนหน้าเข้ากับต้นทุนประสิทธิผลตอนจัดอันดับ (GREEDY_KM_PENALTY = 10 เป็นหน่วยอัตราส่วนคะแนนต่อบาท จึงไม่เท่ากับ 0.3 ตรง ๆ) ในโหมด quality ที่ไม่คิดต้นทุนตอนเลือกสถานที่ ระบบผสม seed แบบ ratio หนึ่งในสามของประชากรเริ่มต้น การเลือกโรงแรมหักคะแนนด้วย 0.08 คูณ (ระยะมัธยฐานถึงสถานที่ท่องเที่ยว บวกระยะเฉลี่ยถึงร้านอาหาร 8 ร้านที่ใกล้ที่สุด) และกรณีไม่รวมโรงแรมใช้โรงแรมที่ใกล้ที่สุดตามเกณฑ์เดียวกันเป็นจุดเริ่มและจบเท่านั้น
ฝั่งเซิร์ฟเวอร์ (backend/main.py) มีกลไกป้องกันกรณีงบน้อย คือ
- (1) งบกิจกรรมต่อคนของทุกระดับไม่ต่ำกว่าค่าอาหารขั้นต่ำของทริป (ร้านที่ถูกที่สุด 2 มื้อต่อวัน คูณ 1.25) แต่ไม่เกินเงินที่ผู้ใช้มีจริง
- (2) ถ้าแผนของระดับใดผิดข้อจำกัดหรือเกินงบ ให้สร้างใหม่ด้วยตัวเลือกทั้งหมดและสุ่มใหม่สูงสุด 3 ครั้ง แล้วเลือกแผนที่ผ่านและคะแนนสูงสุด
- (3) ถ้าที่พักถูกสุดรวมค่าอาหารขั้นต่ำเกินงบ ให้สร้างแผนแบบไม่รวมโรงแรมแทนพร้อมแจ้งผู้ใช้
- (4) เมื่องบไม่พอจะให้สถานที่ท่องเที่ยวครบ 4 แห่งทุกวันก่อน ส่วนมื้ออาหารเป็นรอง (_prioritize_sights ใช้เฉพาะแพ็กเกจจากหน้าเว็บ ไม่ได้ใช้ในการทดลองบทที่ 4) โดยถอดร้านอาหารก่อนถ้าเกินงบ เติมสถานที่ท่องเที่ยวที่เพิ่มระยะทางน้อยที่สุด แล้วเติมร้านอาหารคืนให้วันแรก ๆ เท่าที่งบเหลือ และถ้าวันที่ที่เที่ยวไม่ครบขับเกิน 120 กิโลเมตร ให้ล้างวันนั้นแล้วสร้างใหม่จากสถานที่ใกล้โรงแรม
ผลการทดสอบแบบกวาดทุกจังหวัดอยู่ในหัวข้อ 4.3
### การออกแบบ Chromosome Representation
เนื่องจากปัญหาเป็น multi-day การออกแบบ chromosome ต้องสามารถแทนทริปหลายวันที่มีจำนวนจุดต่างกันในแต่ละวันได้ โครงงานนี้เลือกใช้ list of lists โดยแต่ละ inner list คือ sequence ของ POI index ในแต่ละวัน วิธีนี้ทำให้ crossover และ mutation operator มีความซับซ้อนขึ้น เพราะต้องระวังการเปลี่ยนแปลงข้ามวัน ตัวอย่างโครงสร้างและการทำ crossover ระดับวันแสดงในภาพที่ 3.5

ภาพที่ 3.5 ตัวอย่าง chromosome (รายวัน) และ crossover ระดับวัน
### การจัดการ Constraint Violation
ปัญหา B-TOPTW มี constraint หลายชั้น (งบ, เวลาต่อวัน, time window) การ encode constraint เป็น hard constraint ทำให้ search space แคบเกินไป โครงงานนี้จึงใช้ soft constraint ผ่าน penalty function โดย fitness = total_score - penalty(constraint violations) เพื่อให้ GA ค้นหาคำตอบได้กว้างขึ้น
### การปรับสมดุลระหว่าง Exploration และ Exploitation
การกำหนดค่า mutation rate และ crossover rate มีผลต่อความสามารถในการสำรวจ search space (exploration) เทียบกับการปรับปรุงคำตอบที่ดีอยู่แล้ว (exploitation) โครงงานใช้ GA ที่ประชากร 50 รุ่น 100 และ mutation rate 0.3 ส่วน Hybrid ใช้ประชากร 30 รุ่น 60 และ mutation rate 0.3 เพราะมีขั้นเริ่มต้นจาก Greedy และขั้นปรับปรุงเฉพาะที่ช่วยอยู่แล้ว ค่าเหล่านี้ใช้เหมือนกันในการทดลองทุกชุดของบทที่ 4 และตรวจผลกระทบของพารามิเตอร์ที่สำคัญกว่าในหัวข้อการวิเคราะห์ความไว
### Hybrid Algorithm
เนื่องจาก Greedy Algorithm มีข้อจำกัดเชิง locally optimal (เลือกจุดดีที่สุดทีละขั้นโดยไม่คิดถึงวันถัดไป) ทำให้วันท้าย ๆ ของทริปยาวมักขาดสถานที่ท่องเที่ยว ส่วน Genetic Algorithm แม้จะให้ผลลัพธ์ดีในเชิง global optimization แต่ใช้เวลามาก (ประมาณ 3-9 วินาทีต่อการเรียกในการทดลองบทที่ 4) และโครงสร้างวันไม่แน่นอน โครงงานจึงนำเสนอ Hybrid Algorithm ที่รวมข้อดีของทั้งสองวิธี ดังนี้
- (1) Greedy Seeding: ใช้ Greedy slot-based สร้าง initial population โดยใช้ multiple greedy starts (สลับลำดับ POI) เพื่อความหลากหลาย
- (2) GA Refinement: ใช้ GA evolve population ด้วย operator ที่ออกแบบให้รักษา slot pattern (slot_repair function) มี adaptive mutation rate (ค่าลดลงตามจำนวน generation) และ early stopping (หยุดถ้าไม่มี improvement 15 generations)
- (3) 2-opt Local Search: หลัง GA จบ ใช้ 2-opt swap optimize ลำดับ attractions ในแต่ละวันเพื่อลด travel distance โดยรักษาตำแหน่ง slot 3 (lunch) และ slot 6 (dinner) ไว้
- (4) Insertion Local Search (ILS): หลัง 2-opt และการซ่อมแผน ใช้การค้นหาเฉพาะที่แบบแทรก/แทนที่ในแต่ละวัน (รายละเอียดหัวข้อ 3.3.12) รับผลเฉพาะเมื่อแผนยังผ่านทุกข้อจำกัดและ fitness ไม่แย่ลง
- (5) ซ่อมแผน: ซ่อมเวลาและเวลาปิด ซ่อมงบ และเติมมื้อที่ขาด โดยวันที่แน่นจนไม่มีเวลาใส่มื้อจะถอดสถานที่ท่องเที่ยวคะแนนต่ำสุดก่อนเติมมื้อ (เฉพาะเมื่อมีร้านอาหารพอสำหรับทั้งทริป ถ้าร้านไม่พอการถอดไม่ช่วยให้ได้มื้อเพิ่ม) เพื่อรับประกันว่าแผนผ่านข้อจำกัดและมีมื้อครบทุกวัน
Hybrid Algorithm (รวม ILS) ทำงานในเวลาเฉลี่ยประมาณ 569-1454 มิลลิวินาทีต่อครั้งในการทดลองบทที่ 4 (ตารางที่ 4.2) เร็วกว่า GA ที่ใช้เวลา 2985-8553 มิลลิวินาที และให้โครงสร้างวันที่สมจริง จึงเหมาะกับระบบที่ต้องการทั้งคุณภาพและความเร็วในการตอบสนอง ลำดับขั้นตอนของ Hybrid แสดงในภาพที่ 3.6

ภาพที่ 3.6 ขั้นตอนของ Hybrid Algorithm (Greedy seed, GA, 2-opt, ILS, ซ่อมแผน และตรวจข้อจำกัด)
### Free-Attraction Fallback Mechanism (สำคัญสำหรับงบจำกัด)
เพื่อรองรับงบจำกัด (เริ่มต้นที่ 1000 บาท) ระบบมี fallback หลายขั้นให้ทุกวันมีกิจกรรมแม้งบหมด แต่ละช่องของวันเริ่มจากการหา POI ปกติภายในงบรายวัน แล้วหากไม่พบจึงถอยตามลำดับ คือ
- (1) ช่องมื้ออาหาร: ขยายงบมื้อเป็นอย่างน้อย 300 บาทหรือครึ่งหนึ่งของงบที่เหลือ
- (2) ช่องมื้ออาหาร: เลือกร้านใดก็ได้โดยไม่สนงบ
- (3) เลือกเฉพาะ POI ฟรี
- (4) ช่องสถานที่ท่องเที่ยวก่อนมื้อกลางวัน: หา POI ในงบรายวันโดยไม่กันเวลาสำหรับมื้อเย็น (โค้ดมีขั้นขยายช่วงเวลามื้อด้วย แต่ค่าปัจจุบันเท่ากับช่วงปกติจึงไม่ได้ผ่อนเวลาจริง)
ผลคือผู้ใช้ที่งบ 1,000 บาท 4 วัน ยังได้ทุกวัน 6 จุด (เน้นจุดฟรี เช่น หาด วัด จุดชมวิว เมืองเก่า)
### Insertion Local Search (ILS)
ILS ปรับปรุงแผนที่ Hybrid สร้างแล้วในแต่ละวัน โดย
- (1) แทนที่สถานที่แต่ละช่องด้วยสถานที่ที่ยังไม่ใช้ในหมวดเดียวกัน เมื่อวัตถุประสงค์ดีขึ้นและยังผ่านเวลา เวลาปิด และงบ
- (2) เติมสถานที่ท่องเที่ยวในวันที่มีไม่ถึง 4 จุด ณ ตำแหน่งที่ดีที่สุด
- (3) shake คือแทนที่ 2 จุดแบบสุ่มแล้วค้นหาซ้ำ เก็บแผนที่ดีที่สุด 8 รอบ วัตถุประสงค์ต่อวันคือคะแนนรวม บวกความหลากหลายตามน้ำหนัก w ลบ 0.3 ต่อกิโลเมตรที่ขับ (ดูหัวข้อ 3.3.6) ลบ 0.02 ต่อนาทีที่รอก่อนมื้อ และลบ 0.01 ต่อนาทีของเวลาทั้งวัน
ILS จำเป็นเพราะ GA สลับสถานที่แบบสุ่ม จึงมักปล่อยให้บางวันเหลือจุดน้อยกว่าที่เวลาอนุญาต ผลการวัดอยู่ที่ตารางที่ 4.6
การหักคะแนนเวลาทั้งวัน (TIME_WEIGHT = 0.01 ต่อนาที นับจากออกโรงแรม 08:00 จนกลับถึงโรงแรม) ใช้ทั้งใน fitness ของ Hybrid และใน ILS เพื่อให้ 6 จุดต่อวันเป็นวันที่กระชับ ไม่ใช่เพิ่มจำนวนจุด จากการวัดเบื้องต้น (S2, 6 seed, 3 จังหวัด) ค่านี้ลดความยาววันเฉลี่ยราว 1 ชั่วโมง โดยคะแนนลดลงไม่ถึงร้อยละ 0.6 ส่วนการสลับสถานที่ข้ามวันและการขยายการค้นหาของ ILS เปลี่ยนคะแนนเพียงราว ±0.1% และ ±0.4% (วิธีหลังใช้เวลาเป็นสองเท่า) จึงไม่นำมาใช้ ความยาววันที่วัดด้วยโมเดลค่าเดินทางปัจจุบันเฉลี่ย 10.8 ชั่วโมงต่อวัน (รายจังหวัด 10.3-11.2 ช่วง 9.8-13.2; S2, 6 seed, 4 จังหวัด)
ขั้นซ่อมงบ (_budget_repair) ตัดจากวันที่มีสถานที่มากที่สุดก่อน และแทนที่สถานที่ที่แพงที่สุดด้วยสถานที่ที่ถูกกว่าและคะแนนสูงสุดในวันเดียวกันก่อนลบทิ้งถ้าไม่มีตัวแทน เพื่อไม่ให้การลบกระจุกที่วันใดวันหนึ่ง (ตรวจ 9 รอบ จำนวนสถานที่ต่อวันต่างกันไม่เกิน 1 จุด) สำหรับกรณีงบน้อยมากและไม่รวมโรงแรม (เช่น นครนายก งบ 2,000 บาท ที่โรงแรมถูกสุดอยู่ไกลร้านอาหารจนแผนเหลือแต่ร้านอาหาร) ระบบ
- (1) เลือกโรงแรมฐานจากระยะถึงแหล่งท่องเที่ยวและร้านอาหาร 8 ร้านที่ใกล้ที่สุด
- (2) ให้ระดับ Budget และ Standard ใช้งบ 60 และ 85 เปอร์เซ็นต์ของงบทั้งหมดเมื่อไม่รวมโรงแรม
- (3) รับประกันงบกิจกรรมอย่างน้อย 40 เปอร์เซ็นต์ของเงินที่เหลือเมื่อโรงแรมแพงกว่าส่วนที่จัดไว้
- (4) ให้ขั้นซ่อมงบสลับร้านอาหารให้ค่าใช้จ่ายรวมต่ำสุดก่อน และไม่ตัดสถานที่ถ้าตัดหมดแล้วก็ยังเกินงบ พร้อมแจ้งผู้ใช้ว่างบไม่พอ
ผลการทดสอบอยู่ในหัวข้อ 4.3
### ความหลากหลายของหมวดใน fitness
เพื่อให้ Hybrid คำนึงถึงมากกว่าคะแนนอย่างเดียว (วัตถุประสงค์หลายข้อแบบ weighted-sum) ฟังก์ชัน fitness เพิ่มโบนัส w × (จำนวนหมวด attraction ที่ต่างกันต่อวัน − 1) และหักคะแนน w × จำนวนจุดที่ซ้ำหมวดเกิน 2 จุดต่อวัน โดยใช้ w = 1.5 ทั้งในการสร้างแผนและในการปรับแผนใหม่ ผู้ใช้เห็นผลเป็นทริปที่ครอบคลุมหลายประเภทสถานที่มากขึ้นในแต่ละวัน
### แนวทางเสริม: NSGA-II และ Reinforcement Learning
นอกจากการถ่วงน้ำหนักความหลากหลายแบบ weighted-sum โครงงานเพิ่ม NSGA-II (algorithm/pareto.py) ที่เพิ่มประสิทธิภาพพร้อมกัน 3 วัตถุประสงค์ คือคะแนนรวม (มากสุด) ความหลากหลายของหมวดต่อวัน (มากสุด) และระยะขับรวม (น้อยสุด) จัดการข้อจำกัดด้วย constraint-domination ของ Deb ใช้ประชากร 40 generations 40 แล้วซ่อมผลด้วย meal_fill, 2-opt และซ่อมเวลาและงบ กรองเหลือเฉพาะ front ที่ผ่านทุกข้อ ผู้ใช้กดปุ่มทางเลือก (/api/pareto) เพื่อดูแผนทางเลือกและเลือกเป็นแพ็กเกจปัจจุบันได้ ผลเทียบกับ Hybrid ถ่วงน้ำหนักอยู่ที่ตารางที่ 4.8 หน้าจอแสดงเป็นการ์ดติดป้ายตามจุดเด่น ไม่แสดงตัวเลขคะแนนแก่ผู้ใช้ทั่วไป
โครงงานทดลองใช้ Reinforcement Learning สร้างแผนเริ่มต้นแทน Greedy seed (algorithm/rl.py) โดย policy เป็น softmax เชิงเส้นบนลักษณะเฉพาะ 9 ตัวของสถานที่ผู้สมัครในแต่ละช่องของวัน (เช่น คะแนน ค่าใช้จ่ายเพิ่ม เวลาเหลือ เวลารอ ความหลากหลาย) ฝึกด้วย REINFORCE 2,400 episodes บน 4 จังหวัด × 3 สถานการณ์ แล้วใช้เป็น seed ของ Hybrid (Hybrid+RL) ผลในตารางที่ 4.7 ไม่ดีกว่า Hybrid จึงพักแนวทางนี้ไว้ (เปิดให้ทดลองเฉพาะโหมด Developer)
### การปรับแผนใหม่ด้วย Hybrid (Re-optimization)
เมื่อผู้ใช้สลับ เพิ่ม หรือลบสถานที่ในแพ็กเกจ ระบบคำนวณเวลาและค่าใช้จ่ายใหม่ตามที่ผู้ใช้สั่งโดยตรง (/api/recompute) พร้อมคำเตือนเมื่ออาจไปไม่ทันเวลาปิด เพราะจากการทดสอบบนหน้าเว็บพบว่าการให้ Hybrid ปรับแผนทุกครั้งที่ผู้ใช้เพิ่มสถานที่ทำให้สถานที่อื่นถูกถอดเอง (เช่น เพิ่มกิจกรรมล่องเรือ 8 ชั่วโมงแล้วสถานที่อื่นของวันนั้นหายหมดเพราะเต็มเพดานเวลา) ซึ่งขัดกับเจตนาผู้ใช้ มีปุ่มย้อนกลับและเดินหน้า (undo/redo, Ctrl+Z และ Ctrl+Y) เก็บแผนหลังการแก้แต่ละครั้งได้สูงสุด 50 ขั้น และเริ่มประวัติใหม่เมื่อสร้างแผนใหม่ ส่วน endpoint /api/reoptimize ที่รัน Hybrid ปรับทั้งแพ็กเกจจากแผนปัจจุบันยังอยู่ในระบบ โดยจุดที่ผู้ใช้เลือกเองถูกล็อกไว้ในแผนและจุดที่ผู้ใช้ลบถูกห้ามกลับเข้ามา ตารางที่ 4.4 วัดการปรับแผนนี้ แต่หน้าเว็บไม่เรียกใช้หลังผู้ใช้แก้แผน
อัลกอริทึม reoptimize_solve เป็น evolutionary search แบบ (mu+lambda) ที่ใช้เฉพาะ mutation เริ่มจากแผนปัจจุบัน ทิ้งผลลัพธ์ที่ละเมิดจุดล็อกหรือจุดที่ลบ จัดลำดับด้วย 2-opt แล้วเข้ารอบซ่อมที่วนซ้ำจนแผนผ่านทุกข้อจำกัดและมีมื้อครบ ได้แก่ ซ่อมเวลาและเวลาปิด ซ่อมงบ เติมมื้อที่ขาด (ขยายช่วงเวลาเข้าร้านเมื่อจำเป็น) และตรวจแต่ละวัน หากจุดที่ผู้ใช้ล็อกเป็นกิจกรรมเฉพาะช่วงเย็นและชนกับมื้อเย็น ระบบย้ายไปท้ายวันก่อน และถอดออกถ้ายังไม่ผ่านพร้อมแจ้งผู้ใช้ จุดที่ใส่ในแผนไม่ได้อยู่แล้ว (เวลาเปิด-ปิด งบ หรือเวลาต่อวันไม่พอ) จะถูกแจ้งตั้งแต่ก่อนปรับแผน ลำดับขั้นตอนแสดงในภาพที่ 3.7

ภาพที่ 3.7 ขั้นตอนของการปรับแผนใหม่ด้วย Hybrid (re-optimization)
### ความชอบของผู้ใช้ (User Preference)
ผู้ใช้ระบุความชอบก่อนค้นหา 3 ด้าน ได้แก่ หมวดสถานที่ที่ชอบ หมวดที่ไม่ต้องการ และความต้องการด้านอาหาร (มังสวิรัติหรือฮาลาล) ระบบนำความชอบไปกรองและถ่วงน้ำหนัก POI ก่อนส่งให้อัลกอริทึม (ฟังก์ชัน apply_preferences) โดยหมวดที่ไม่ต้องการถูกตัดออกจากตัวเลือก หมวดที่ชอบได้คะแนนถ่วงเพิ่ม 1.0 ซึ่งใช้ในการเลือกเท่านั้น คะแนนที่รายงานแก่ผู้ใช้ยังเป็นคะแนนจริง และช่วงคะแนนของแต่ละระดับแพ็กเกจคำนวณจากคะแนนจริง ความชอบเดียวกันใช้กับการปรับแผนหลังผู้ใช้แก้ไขด้วย
ความต้องการด้านอาหารใช้แท็กอาหารของร้านจาก OpenStreetMap (diet และ cuisine) ถ้าร้านที่ตรงมีอย่างน้อย 2 x จำนวนวัน + 2 ร้าน ระบบใช้เฉพาะร้านเหล่านั้น ถ้าน้อยกว่าจะถ่วงคะแนนร้านที่ตรงให้ถูกเลือกก่อนแล้วเสริมด้วยร้านทั่วไป พร้อมแจ้งผู้ใช้ว่าไม่รับประกันว่ารองรับ ข้อมูลปัจจุบัน: ร้านมังสวิรัติเชียงใหม่ กระบี่ และสมุยจังหวัดละ 12 ร้าน (เชียงใหม่เป็นมังสวิรัติเจ 7) ร้านฮาลาลมีที่กระบี่ 7 และภูเก็ต 8 ร้าน ไม่มีที่เชียงใหม่และสมุย ร้านอาหารที่คัดเองของภูเก็ตไม่มีแท็กอาหาร จึงเสริมร้านมังสวิรัติ 12 และฮาลาล 8 ร้านจาก OSM (รวม 17 ร้านที่ไม่ซ้ำกัน) ความต้องการ "หลีกเลี่ยงสถานที่คนพลุกพล่าน" ไม่ได้ทำ เพราะไม่มีข้อมูลความหนาแน่นของผู้คน
### การส่งออกแผน (Export)
ผู้ใช้ส่งออกแผนได้ 2 รูปแบบ คือไฟล์ปฏิทิน (.ics ตามมาตรฐาน RFC 5545) และ PDF ไฟล์ปฏิทินสร้างที่ฝั่งหน้าเว็บจากตารางเวลาที่อัลกอริทึมคำนวณ (backend ส่งเวลาถึงของแต่ละจุดในฟิลด์ arrivals) แต่ละสถานที่เป็น 1 กิจกรรม เริ่มตามเวลาถึงและยาวตามระยะเวลาที่ใช้ มีพิกัดและหมวด เริ่มวันแรกตามวันเช็คอินที่ผู้ใช้เลือก ใช้เวลาแบบ local (floating) เพื่อเปิดได้ใน Google Calendar, Apple Calendar และ Outlook ส่วน PDF ใช้หน้าพิมพ์ของเบราว์เซอร์ร่วมกับ print stylesheet ที่แสดงเฉพาะรายละเอียดทริป แล้วให้ผู้ใช้เลือกบันทึกเป็น PDF
### การวางแผนร่วมกัน (Collaborative Planning)
ผู้ใช้กดปุ่มแชร์เพื่อสร้างลิงก์ให้เพื่อนเปิดดูและแก้แผนเดียวกัน backend เก็บแผนในหน่วยความจำและไฟล์ data/sessions.json (endpoint /api/sessions) แต่ละ session มีเลขเวอร์ชัน การบันทึกต้องส่งเวอร์ชันที่แก้จาก ถ้าไม่ตรงกับปัจจุบัน backend ตอบ 409 Conflict เพื่อกันการเขียนทับกัน หน้าเว็บสอบถามการเปลี่ยนแปลงทุก 2 วินาที session หมดอายุหลัง 24 ชั่วโมงและเก็บได้สูงสุด 300 session กลับมาหลังรีสตาร์ทได้ (ทดสอบแล้ว) แต่ใช้ไฟล์เดียวบนเครื่องเดียว ไม่รองรับหลายเซิร์ฟเวอร์
### ส่วนติดต่อผู้ใช้และส่วนเสริมของเว็บแอป
ระบบมี 2 โหมด โหมดปกติซ่อนตัวเลือกอัลกอริทึมและคะแนนภายใน ใช้ Hybrid เสมอและมีเพียงปุ่มค้นหา ส่วนโหมด Developer (ปุ่ม </> บนแถบด้านบนหรือ ?dev=1) เปิดให้สลับ Greedy, GA, Hybrid และ Hybrid+RL เปรียบเทียบผล และดูหน้าสรุปผลการทดลอง ส่วนติดต่อใช้โทนส้มเข้มและไอคอนเส้นบาง SVG ชุดเดียว รองรับจอมือถือ (เรียงคอลัมน์เดียว แผนที่สูงราว 62% ของจอ ตรวจที่ความกว้าง 375 พิกเซล ไม่พบการเลื่อนแนวนอน) ผู้ใช้เปิด-ปิดการแสดงผลรายวันบนแผนที่ (day filter) ลากวางสถานที่เพื่อเรียงลำดับหรือย้ายข้ามวัน (จอสัมผัสกดค้างราว 0.35 วินาที) ย้อนกลับและเดินหน้าได้ และดูรายละเอียดสถานที่ (เวลาเปิด-ปิด ค่าใช้จ่าย เวลาถึง) พร้อมปุ่มเปิด Google Maps ที่ค้นหาด้วยชื่อสถานที่และจังหวัด (ไม่ใช้พิกัด OSM ที่บางจุดคลาดเคลื่อน) รีวิวเป็นข้อมูลจำลองที่ติดป้ายกำกับ ไม่ได้ใช้คำนวณแผนหรือผลการทดลอง มีระบบแนะนำการใช้งาน (tutorial) เมื่อเข้าใช้ครั้งแรก
เพื่อให้ใช้งานได้กับจังหวัดที่ข้อมูลไม่เท่ากัน ระบบจำกัดจำนวนวันสูงสุดต่อจังหวัดตามข้อมูล (สถานที่ไม่น้อยกว่า 3 จุดและร้านอาหารไม่น้อยกว่า 2 ร้านต่อวัน) ติดป้ายข้อมูลน้อย บันทึกและเปิดแผนที่เคยสร้างในเบราว์เซอร์ และสลับภาษาไทย/อังกฤษได้ ด้านสภาพอากาศ ระบบดึงพยากรณ์รายวันจาก Open-Meteo [15] ล่วงหน้าราว 16 วัน เมื่อโอกาสฝนตั้งแต่ร้อยละ 60 ในวันที่มีสถานที่กลางแจ้ง จะมีปุ่มสลับเป็นพิพิธภัณฑ์หรือตลาดภายใน 25 กิโลเมตรที่ยังไม่อยู่ในแผน คำนวณใหม่เฉพาะวันนั้นและคืนแผนเดิมหากผิดข้อจำกัด วันที่เกินช่วงพยากรณ์ใช้หมายเหตุภูมิอากาศรายเดือนแทน กล่อง Tips สร้างจากแม่แบบด้วยข้อมูลจริงของสถานที่ ไม่ได้ใช้แบบจำลองภาษา

### การออกแบบการทดลอง
ผลการทดลองในหัวข้อนี้รันภายใต้กติกาความสมจริงของแผนรายวัน (หัวข้อ 3.3.5: มื้ออาหารตามเวลาจริง 6 จุดต่อวัน คือสถานที่ท่องเที่ยว 4 และอาหาร 2 เพดานเวลาท่องเที่ยว 8 ชั่วโมงต่อวัน) จึงเปรียบเทียบกับตัวเลขของโครงงานพิเศษ 1 (ตารางที่ 4.1) โดยตรงไม่ได้ ชุดทดลองประกอบด้วย
- (ก) เปรียบเทียบ Greedy, GA, Hybrid และ Hybrid ที่เพิ่มความหลากหลายของหมวดใน fitness (Hybrid+Div) ใน 4 จังหวัด 3 สถานการณ์ (S1: 3 วัน 10,000 บาท, S2: 5 วัน 15,000 บาท, S3: 7 วัน 25,000 บาท) ใช้เวลาเดินทางตามโปรไฟล์ของแต่ละจังหวัด รัน GA และ Hybrid สถานการณ์ละ 15 รอบ (Greedy เป็นวิธีกำหนดแน่นอนจึงรันครั้งเดียว)

- (ง) Insertion Local Search
- (จ) Reinforcement Learning
- (ฉ) Pareto front ด้วย NSGA-II
- (ช) จังหวัดข้อมูลน้อย

### คุณภาพของข้อมูลที่สร้างอัตโนมัติ
การตรวจข้อมูลที่ดึงจาก OSM พบปัญหา 4 ข้อ คือ หมวดกิจกรรมมีน้อย (กระบี่ 1 จุด เชียงใหม่ 5 จุด สมุย 6 จุด) ร้านอาหารทุกร้านถูกตั้งราคาเท่ากัน (200 บาท) ทำให้แพ็กเกจ Budget ซึ่งกรองร้านไม่เกิน 150 บาทไม่มีมื้ออาหารเลย คะแนนสถานที่ซ้ำกันมาก (5-7 ค่า) และมีชื่อภาษาไทยล้วน จึงแก้โดยเพิ่มคำค้นหมวดธรรมชาติ น้ำตก อุทยาน สปา ดำน้ำ โรงเรียนทำอาหาร และร้านจานด่วน ประมาณราคาร้านอาหารจากประเภทอาหาร (cuisine) คัดชื่อที่ไม่ใช่อักษรไทยหรือละตินออก คำนวณคะแนนเป็นค่าต่อเนื่องจากความสมบูรณ์ของข้อมูลใน OSM (wikidata เว็บไซต์ โทรศัพท์ เวลาเปิด-ปิด รูปภาพ และจำนวนแท็ก) และเติมชื่ออังกฤษให้ 23 รายการด้วยการแปลโดยปัญญาประดิษฐ์ ผลคือกิจกรรมเพิ่มเป็น 40 จุด (เชียงใหม่ กระบี่) และ 24 จุด (สมุย) ร้านราคาไม่เกิน 150 บาทมีอย่างน้อย 29 ร้านต่อจังหวัด และคะแนนมี 16-22 ค่าที่ไม่ซ้ำต่อจังหวัด (ภูเก็ต 26 ค่า)

# สรุป
## สรุปผลการดำเนินงาน
โครงงานนี้นำเสนอระบบสร้างและเพิ่มประสิทธิภาพเส้นทางท่องเที่ยวภายใต้งบประมาณด้วยปัญญาประดิษฐ์ โดยนิยามปัญหาเป็น B-TOPTW และเปรียบเทียบ Greedy, GA และ Hybrid Algorithm ที่นำเสนอใหม่ โครงงานพิเศษ 1 พิสูจน์แนวคิดบนภูเก็ต ส่วนโครงงานพิเศษ 2 ต่อยอดให้ใช้ได้ทั้ง 77 จังหวัด โดยมี 4 จังหวัดหลัก (ภูเก็ต เชียงใหม่ กระบี่ เกาะสมุย) รวม 720 สถานที่และ 99 โรงแรมเป็นชุดข้อมูลหลัก และท่อประมวลผลสร้างข้อมูลจังหวัดที่เหลือจาก OpenStreetMap อัตโนมัติ ปรับเทียบเวลาเดินทางรายจังหวัดด้วย OSRM และเพิ่มกติกาความสมจริงของแผนรายวัน, Insertion Local Search, ทางเลือก Pareto, การปรับแผนใหม่, ความหลากหลายของหมวด, ความชอบของผู้ใช้, การส่งออกแผน, การวางแผนร่วมกัน และโหมด Developer
ผลการทดลองใน 4 จังหวัด 3 สถานการณ์ จังหวัดละ 15 รอบ สรุปได้ดังนี้
- (1) Hybrid ได้คะแนนสูงกว่า GA อย่างมีนัยสำคัญ 12 จาก 12 ชุด (ร้อยละ 2.4-5.5) และสูงกว่า Greedy 11 จาก 12 ชุด (ต่ำกว่า 1 ชุดคือเกาะสมุย S3 ร้อยละ 0.5) โดยผ่านข้อจำกัดและมีมื้อครบทุกรอบ
- (2) Insertion Local Search เพิ่มคะแนนร้อยละ 1.9-4.4 อย่างมีนัยสำคัญ 24 จาก 24 ชุด แลกกับเวลาเพิ่มราว 2.1 เท่า
- (3) Hybrid ขับเฉลี่ย 25 กิโลเมตรต่อวัน เทียบกับ GA 39 และ Greedy 58 (Greedy ใช้ค่าปรับคนละหน่วย จึงไม่เท่ากันทุกประการ)
- (4) ความหลากหลายของหมวดลดคะแนนไม่เกินร้อยละ 1.8 แต่เพิ่มจำนวนหมวดต่อวันเป็นราว 3.1-3.8 หมวด
- (5) การปรับแผนด้วย Hybrid หลังผู้ใช้แก้แผนทำให้แผนที่ผ่านข้อจำกัดเพิ่มจาก 137 เป็น 180 จาก 180 กรณี และมีมื้อครบ 180 กรณี
- (6) ความชอบของผู้ใช้ทำงานบางส่วน หมวดที่ไม่เอาไม่ปรากฏในแผนทุกจังหวัด แต่หมวดที่ชอบมีสัดส่วนสูงขึ้นอย่างมีนัยสำคัญเพียง 32 จาก 78 ชุดข้อมูล โดยคะแนนลดลงได้ถึงร้อยละ 63.0 ในบางจังหวัด
- (7) Hybrid+RL ไม่ได้ดีกว่า Hybrid อย่างสม่ำเสมอ (ดีกว่าอย่างมีนัยสำคัญ 2 จาก 20 ชุด และต่ำกว่าอย่างมีนัยสำคัญ 4 ชุด) จึงพักแนวทางนี้ไว้
- (8) NSGA-II ให้แผนทางเลือกมากกว่า (เฉลี่ย 23-28 แผนเทียบกับ 3-4) ในเวลาน้อยกว่า 4-5 เท่า แต่มี hypervolume ต่ำกว่า Hybrid ถ่วงน้ำหนักอย่างมีนัยสำคัญ 3 จาก 4 จังหวัด จึงไม่ควรสรุปว่า NSGA-II ให้คุณภาพดีกว่า
- (9) การใช้ 6 จุดต่อวันทำให้คะแนนรวมต่ำกว่าแบบที่ผ่อนเพดานเป็น 7-8 จุดต่อวัน เพราะมีสถานที่น้อยลง แลกกับแผนที่ไปได้จริงมากขึ้น และการหักคะแนนเวลาทั้งวันทำให้วันสั้นลง
- (10) การวิเคราะห์ความไวแสดงว่าข้อสรุปข้างต้นคงอยู่เมื่อปรับ DIST_WEIGHT, GREEDY_KM_PENALTY, TRAFFIC_FACTOR และ TIME_WEIGHT ในช่วงที่ทดสอบ (ตารางที่ 4.11)
- (11) ชุดทดสอบอัตโนมัติ 26 กรณีผ่านทั้งหมด (ตารางที่ 4.12)
ในจังหวัดข้อมูลน้อย 8 จังหวัด (ตารางที่ 4.9) แผนของ Hybrid ผ่านข้อจำกัดครบทุกรอบและชนะ GA อย่างมีนัยสำคัญ 7/8 (S1), 5/8 (S2) และ 5/8 (S3) ชุดที่ไม่ชนะ (พิจิตร กาฬสินธุ์ ชัยภูมิ สิงห์บุรี) ตรวจสาเหตุในตารางที่ 4.10 พบว่าเกิดจากการเทียบคะแนนดิบของแผนที่ขับระยะต่างกันมาก (ชัยภูมิ) คะแนนที่อิ่มตัวใกล้เพดาน (กาฬสินธุ์ สิงห์บุรี) และขั้นซ่อมแผนของ Hybrid ที่ถอดสถานที่ท่องเที่ยวโดยไม่ได้มื้อเพิ่มเมื่อร้านอาหารไม่พอ (พิจิตร ซึ่งแก้ไขแล้ว)
## อภิปรายผล
เหตุผลที่ Hybrid ได้คะแนนสูงกว่า GA อย่างสม่ำเสมอ (12 จาก 12 ชุด) คือ Hybrid เริ่มจากแผนที่ Greedy สร้างซึ่งมีโครงสร้างวันถูกต้องอยู่แล้ว ส่วน GA เริ่มจากประชากรสุ่มจึงใช้เวลาเพื่อไปถึงโครงสร้างเดียวกันและมักเหลือบางวันที่มีจุดน้อยกว่าที่เวลาอนุญาต Insertion Local Search ช่วยเติมช่องว่างนี้และเพิ่มคะแนนร้อยละ 1.9-4.4 (ตารางที่ 4.6) ในเวลาเพิ่มราว 2.1 เท่า ซึ่งยังเร็วกว่า GA หลายเท่า (ตารางที่ 4.2) และผลที่ได้ไม่ขึ้นกับพารามิเตอร์ที่ผู้พัฒนาเลือกเอง (ตารางที่ 4.11)
การเปรียบเทียบด้วยคะแนนดิบเพียงอย่างเดียวอาจให้ภาพที่คลาดเคลื่อน เพราะอัลกอริทึมที่ไม่ถูกหักระยะขับหรือหักน้อยจะได้คะแนนดิบสูงด้วยแผนที่ขับไกล (เช่น Greedy ในชัยภูมิขับ 174 กิโลเมตรต่อวัน) ผลวินิจฉัยในตารางที่ 4.10 และ 4.11 แสดงว่า Hybrid อยู่บนขอบที่ดีกว่าของความสัมพันธ์ระหว่างคะแนนกับระยะขับ คือที่ระยะขับเท่ากัน Hybrid ได้คะแนนสูงกว่า Greedy และ GA นอกจากนี้ในจังหวัดที่มีข้อมูลมาก คะแนนของทุกวิธีอิ่มตัวใกล้เพดาน (ร้อยละ 94-98) ส่วนต่างของคะแนนดิบจึงเล็กและไม่มีนัยสำคัญ แม้ Hybrid จะขับน้อยกว่า ดังนั้นจุดที่ Hybrid ได้เปรียบชัดที่สุดคือจังหวัดที่ตัวเลือกกระจายตัวและข้อจำกัดตึง
ผลของความชอบจำกัดด้วยปริมาณสถานที่ในหมวดที่ชอบ จาก 78 ชุดข้อมูล ชุดที่หมวดที่ชอบ (กิจกรรมและจุดชมวิว) เพิ่มสัดส่วนอย่างมีนัยสำคัญ (32 ชุด) มีสถานที่หมวดนั้นมัธยฐาน 8.0 จุด ส่วนชุดที่ไม่มีนัยสำคัญ (46 ชุด) มีมัธยฐาน 3.0 จุด โดย 38 ชุดมีไม่เกิน 5 จุด จึงมีตัวเลือกไม่พอที่จะเพิ่มสัดส่วนได้มากในแผน 5 วัน (ต้องใช้สถานที่ท่องเที่ยว 20 จุด) ความสัมพันธ์ระหว่างจำนวนสถานที่ที่ชอบกับการเพิ่มของสัดส่วนเป็นบวกอย่างชัดเจน (Spearman rho = 0.71, p < 0.001) ส่วนอีก 8 ชุดที่มีสถานที่ 6-10 จุดแต่ไม่มีนัยสำคัญ (p = 0.05-0.17 หรือไม่ต่างกัน) ตรวจเพิ่มด้วยการเพิ่มคะแนนถ่วงความชอบ (LIKE_BOOST) จากค่าปัจจุบัน 1.0 เป็น 3.0 และ 5.0 (15 รอบ) พบ 3 สาเหตุ
- (1) 5 ชุด (พังงา แพร่ ประจวบคีรีขันธ์ ระนอง สระบุรี) สัดส่วนเพิ่มอย่างมีนัยสำคัญเมื่อถ่วง 5.0 (p < 0.025) แสดงว่าค่า 1.0 น้อยเกินไปสำหรับจังหวัดเหล่านี้
- (2) 2 ชุด (บึงกาฬ สุราษฎร์ธานี) แผนปกติใช้สถานที่ในหมวดที่ชอบเกือบหมดอยู่แล้ว (5.7 จาก 6 และ 5.0 จาก 6 จุด) จึงไม่มีที่ให้เพิ่ม
- (3) พะเยา สัดส่วนไม่เปลี่ยนแม้ถ่วง 5.0 โดยสถานที่ในหมวดที่ชอบอยู่ไกลโรงแรมเฉลี่ย 29.8 กิโลเมตร เทียบ 15.4 กิโลเมตรของสถานที่ทั้งหมด จึงน่าจะถูกหักคะแนนระยะทางเกินกว่าคะแนนถ่วง (ยังไม่ได้ทดสอบโดยตรง)
คะแนนของสถานที่ในหมวดที่ชอบไม่ต่ำกว่าค่าเฉลี่ย (7.1-7.5 เทียบ 7.2) ผลนี้สอดคล้องกับการที่ความชอบทำงานได้ตามที่ออกแบบ ปัญหาอยู่ที่ปริมาณข้อมูลและน้ำหนักถ่วงคงที่ที่ไม่ปรับตามจังหวัด (ความสัมพันธ์ไม่ได้พิสูจน์เหตุและผลทั้งหมด) การปรับน้ำหนักตามจำนวนสถานที่ในหมวดที่ชอบเป็นแนวทางต่อยอดที่ยังไม่ได้ทำ
ผลเชิงลบของ Hybrid+RL และ NSGA-II รายงานตามจริง Hybrid+RL ไม่ได้ดีกว่า Hybrid ซึ่งอาจเกิดจากนโยบายเชิงเส้นที่เรียบง่ายและ Greedy seed ที่มีคุณภาพสูงอยู่แล้ว ส่วน NSGA-II ให้แผนทางเลือกมากกว่าแต่ hypervolume ต่ำกว่า Hybrid ถ่วงน้ำหนัก ซึ่งอาจเกิดจากงบการค้นหาที่เท่ากันและหลังซ่อมแผนแล้วจุดบนขอบเหลือน้อยลง สมมติฐานทั้งสองยังไม่ได้ทดสอบ จึงไม่ควรใช้สรุปว่าแนวทางเหล่านี้ใช้ไม่ได้ในทุกกรณี
## ข้อจำกัดของผลงาน
ข้อจำกัดของผลงานที่ควรทราบ ได้แก่
- (1) ข้อมูลจังหวัดที่สร้างอัตโนมัติจาก OpenStreetMap มีคะแนนสถานที่เป็นค่าประเมินจากความสมบูรณ์ของข้อมูล ราคาโรงแรมประมาณจากจำนวนดาว และราคาร้านอาหารประมาณจากประเภทอาหาร ไม่ใช่รีวิวหรือราคาจริง
- (2) ข้อมูลร้านอาหารมังสวิรัติและฮาลาลมีน้อยและไม่ได้ตรวจสอบกับร้านจริง
- (3) เวลาเดินทางคิดจากความเร็วรถไม่ติดที่ปรับเทียบด้วย OSRM คูณตัวคูณการจราจร 1.25 และบวกเวลาเผื่อ 10 นาทีต่อการย้ายจุด ซึ่งเป็นสมมติฐานที่ไม่ได้วัดจากการจราจรจริง และไม่นับค่าเดินทางเป็นเงินในงบ (จึงไม่สะท้อนค่าน้ำมันหรือค่าแท็กซี่จริง) พร้อมหักคะแนนระยะทาง 0.3 ต่อกิโลเมตรใน Hybrid และ GA (Greedy บวกค่าปรับ 10 บาทต่อกิโลเมตรตอนจัดอันดับ จึงเปรียบเทียบระยะขับกับ Hybrid ไม่เท่ากันทุกประการ) ซึ่งเป็นค่าที่เลือกเองไม่ได้ปรับจูนเป็นระบบ
- (4) กติกาความสมจริงตั้งขึ้นเองและยังไม่ได้เทียบกับพฤติกรรมนักท่องเที่ยวจริง วันหนึ่งของแผน Hybrid ยาวราว 10-11 ชั่วโมงรวมการเดินทางและการรอ (S2, 6 seed, 4 จังหวัด เฉลี่ย 10.8 ชั่วโมง รายจังหวัด 10.3-11.2 ช่วง 9.8-13.2)
- (5) Greedy ยังได้แผนสั้นในบางกรณีที่โรงแรมไกลและงบตึง
- (6) ระบบยังไม่ผ่านการทดสอบกับของจริง คือ ไฟล์ปฏิทิน (.ics) ยังไม่ได้นำเข้าในโปรแกรมปฏิทินจริง ส่วนติดต่อผู้ใช้ทดสอบบนเบราว์เซอร์เดียวด้วยเหตุการณ์ลากจำลอง ยังไม่ได้ทดสอบกับเมาส์และอุปกรณ์สัมผัสจริง การวางแผนร่วมกันทดสอบบนเครื่องเดียว ไม่ได้ทดสอบกับผู้ใช้หลายคนบนเครื่องต่างกัน และยังไม่ได้ทดสอบกับผู้ใช้จริง
- (7) ข้อมูล 39 จาก 77 จังหวัดเป็นแบบเบาบาง (สถานที่ 20 จุดขึ้นไปและโรงแรม 2 แห่งขึ้นไป) บางจังหวัดมีโรงแรมน้อยมาก (เช่น อำนาจเจริญ 2 แห่ง) แผนหลายวันจึงมีตัวเลือกที่พักจำกัด หน้าเว็บจึงแสดงป้าย "ข้อมูลน้อย" จำกัดจำนวนวันสูงสุดตามข้อมูลของจังหวัด (สถานที่ไม่น้อยกว่า 3 จุดและร้านอาหารไม่น้อยกว่า 2 ร้านต่อวัน เช่น ปัตตานีและอำนาจเจริญเลือกได้ 1 วัน เพราะมีร้านอาหาร 2 ร้าน) และแจ้งเตือนเมื่อแผนมีวันที่ไม่มีกิจกรรม (เช่น ปัตตานีแผน 5 วันมีวันว่าง 2-4 วัน) จังหวัดที่มีโรงแรมไม่ถึง 3 ระดับราคาใช้โรงแรมซ้ำข้ามแพ็กเกจ ข้อมูลของจังหวัดข้างเคียงมีสถานที่ซ้ำบริเวณชายแดนเล็กน้อย (สูงสุด 16 จุด เช่น กรุงเทพฯกับนนทบุรี ชัยนาทกับอุทัยธานี)
- (8) ตำแหน่งหมุดบนแผนที่มาจากพิกัด OpenStreetMap ซึ่งบางจุดเป็นจุดกึ่งกลางของพื้นที่ จึงคลาดเคลื่อนเล็กน้อยและไม่ตรงกับหมุด Google Maps ทุกจุด ยังไม่ได้วัดขนาดความคลาดเคลื่อน ระบบจึงมีปุ่มเปิด Google Maps ด้วยชื่อสถานที่และจังหวัดให้ผู้ใช้ตรวจตำแหน่งจริง (การดึงพิกัดจาก Google เป็นชุดใหญ่ต้องใช้ API ที่มีค่าใช้จ่ายและเงื่อนไขการแสดงผล จึงไม่ได้ทำ)
- (9) การทดลองหลักรันบน 4 จังหวัดเท่านั้น
- (10) ในพิจิตร แม้แก้ขั้นซ่อมแผนแล้ว Hybrid ยังได้ค่าเป้าหมายต่ำกว่า GA เล็กน้อยเพราะขับไกลกว่า และ S3 สูงกว่า GA แต่ไม่ถึงระดับนัยสำคัญ (ตารางที่ 4.9-4.10)
- (11) การวิเคราะห์ความไวทำทีละพารามิเตอร์ใน S2 เท่านั้น (ตารางที่ 4.11)
- (12) น้ำหนักถ่วงความชอบเป็นค่าคงที่ (1.0) ไม่ปรับตามจังหวัด ผลของความชอบจึงไม่เด่นในจังหวัดที่ถ่วงน้อยเกินไปหรือสถานที่ที่ชอบอยู่ไกลโรงแรม
## ข้อเสนอแนะและแนวทางต่อยอด
แนวทางต่อยอด ได้แก่ การใช้รีวิว ราคา และเวลาเปิด-ปิดจริงจากบริการภายนอก (เช่น Google Places API ซึ่งเลื่อนไว้เพราะต้องผูกบัญชีชำระเงิน) การเสริมข้อมูลจังหวัดแบบเบาบางจากแหล่งอื่นนอกเหนือจาก OpenStreetMap การทดลอง Reinforcement Learning ในรูปแบบอื่น (เช่น เรียนรู้ตัวดำเนินการของ GA หรือ ILS แทนการเป็น seed) การวางแผนทริปข้ามจังหวัดแบบแบ่งช่วงวัน โดยมีโรงแรมและข้อมูลแยกต่อช่วง (เคยทดลองรวมข้อมูลหลายจังหวัดเป็นชุดเดียวแล้วพบว่าแผนเลือกเฉพาะจังหวัดที่โรงแรมตั้งอยู่ จึงถอดฟังก์ชันนี้ออกจากระบบ) การเก็บ session ร่วมกันในฐานข้อมูลถาวร การปรับกติกาความสมจริงตามข้อมูลพฤติกรรมจริง และการทดสอบการใช้งานกับผู้ใช้จริง

ในการพัฒนาโครงงานนี้ ผู้จัดทำใช้เครื่องมือ Generative AI เพียงตัวเดียว คือ Claude ของบริษัท Anthropic (ใช้ผ่านโปรแกรม Claude Code และแอป Claude) ไม่ได้ใช้เครื่องมือ Generative AI อื่น ส่วนของโครงงานที่ใช้ วัตถุประสงค์ และวิธีตรวจสอบผลลัพธ์สรุปในตารางที่ ก.1

ภาคผนวก ค. ตัวอย่างโครงสร้างข้อมูล POI และโรงแรม
ฐานข้อมูลสถานที่ท่องเที่ยวภูเก็ตจัดเก็บในรูปแบบ JSON ไฟล์ data/provinces/phuket.json (จังหวัดอื่นใช้โครงสร้างเดียวกันในโฟลเดอร์ data/provinces) ประกอบด้วย 2 ส่วนหลัก คือ pois (164 รายการ) และ hotels (20 รายการ) โดยมีโครงสร้างฟิลด์ดังตารางต่อไปนี้
ตารางที่ ค.1 โครงสร้างฟิลด์ของข้อมูล POI
| ฟิลด์ | ประเภท | คำอธิบาย |
| --- | --- | --- |
| name_en | String | ชื่อสถานที่เป็นภาษาอังกฤษ |
| name_th | String | ชื่อสถานที่เป็นภาษาไทย |
| category | String | หมวดหมู่ (beach, temple, restaurant, viewpoint, market, culture, activity) |
| lat / lng | Float | พิกัดละติจูด / ลองจิจูด (WGS84) |
| score | Float | คะแนนความน่าสนใจ ช่วง 1.0–10.0 |
| cost | Integer | ค่าใช้จ่ายต่อคน (บาท) — 0 หมายถึงไม่มีค่าเข้า |
| duration_min | Integer | เวลาที่แนะนำในการเยี่ยมชม (นาที) |
| open_min | Integer | เวลาเปิด นับจากเที่ยงคืน (นาที) เช่น 360 = 06:00 |
| close_min | Integer | เวลาปิด นับจากเที่ยงคืน (นาที) เช่น 1320 = 22:00 |
| tags | Array | ป้ายกำกับสำหรับการค้นหาและกรองข้อมูล |
| id | String | รหัสเฉพาะ เช่น P01, P51 (POI) หรือ H01 (Hotel) |
ตารางที่ ค.2 ตัวอย่างข้อมูล POI จากฐานข้อมูล
| ชื่อสถานที่ | หมวดหมู่ | Score | Cost (฿/คน) | เวลาเปิด-ปิด |
| --- | --- | --- | --- | --- |
| Patong Beach | beach | 8.5 | 0 | 06:00–22:00 |
| Wat Chalong | temple | 8.2 | 0 | 07:00–17:00 |
| Kan Eang@Pier | restaurant | 8.5 | 400 | 11:00–22:00 |
| Big Buddha | culture | 9.0 | 0 | 06:00–19:30 |
| ATV Phuket | activity | 7.8 | 1200 | 09:00–17:00 |
| Rawai Seafood Market | market | 7.5 | 300 | 08:00–22:00 |
หมายเหตุ: open_min และ close_min คือจำนวนนาทีนับจากเที่ยงคืน เช่น open_min=360 หมายถึงเปิดเวลา 06:00 น. และ close_min=1320 หมายถึงปิดเวลา 22:00 น.
ตารางที่ ค.3 ตัวอย่างข้อมูลโรงแรมทั้ง 3 ระดับ
| ชื่อโรงแรม | ดาว | ราคา/คืน (฿) | Score | ระดับ |
| --- | --- | --- | --- | --- |
| Lub d Phuket Patong | 1 | 450 | 7.8 | Budget |
| Novotel Karon Beach | 4 | 3500 | 8.6 | Standard |
| Anantara Layan Phuket | 5 | 8000 | 9.4 | Premium |
โรงแรมแบ่งเป็น 3 tier ตามจำนวนดาวและราคา: Budget (1-2 ดาว ≤ 1,500 บาท/คืน), Standard (3-4 ดาว 1,500–5,000 บาท/คืน) และ Premium (4-5 ดาว > 5,000 บาท/คืน) โดย Backend จะเลือกโรงแรมที่เหมาะสมกับงบประมาณในแต่ละ tier อัตโนมัติ
